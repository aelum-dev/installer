## [Unreleased]

### Fixed
- **Manual-mode confirmation partition table no longer overflows the right page column and now renders a clean rounded border** — the plan was laid out with a flex row of grid cells using `fr` columns stretched to `width: 100%`, which pushed the table wider than `page-content` (clipped by its `overflow: hidden`) and left an empty gap in the FS column. Rewrote it as a native `<table>` (`<thead>`/`<tbody>`, `border-spacing: 0`) so every column aligns automatically; the SIZE column is right-aligned so numbers line up under the header. Removed `overflow: hidden` and `border-collapse` from the table (replaced with `border-spacing: 0`), which were clipping the rounded border at the corners. Added the new table-column labels (`NAME`/`SIZE`/`ROLE`) and shortened the FS label to `FS` in `en-US.json`.
- **Confirmation dialog no longer fails to re-open after pressing Cancel or Confirm** — the shared `ConfirmDialog` drives its visibility from a `show` prop created with `$bindable(installState.showConfirmDialog)`, but `App.svelte` rendered `<ConfirmDialog />` with no `bind:`. In Svelte 5 a `$bindable()` default only syncs once when the parent doesn't bind, so the dialog opened the first time the flag was set, but once the child wrote `show = false` back on Cancel/Confirm the link detached and later flag sets were ignored. Fixed by binding in both callers: `App.svelte` now uses `bind:show={installState.showConfirmDialog}` for the install confirmation, and `ManualPartitionPage` uses `bind:show={showDeleteDialog}` for the delete dialog (its old one-way `show={showDeleteDialog}` never reset the flag on dismiss, so a second delete wouldn't re-open it).
- **Manual partitioning no longer rejects a fully-partitioned disk where free space is smaller than the GPT backup region** — `Validate`'s strict new-partition guard (`newSectors > freeSectors - gptBackupSectors`) fired even when there were zero new partitions (`newSectors == 0`), because existing rows can leave fewer free sectors than the trailing GPT backup area. Added a `newSectors > 0` guard so the check only applies when brand-new partitions are actually being added.
- **Manual partitioning slider no longer snaps to the middle after deleting a partition** — deleting a row makes the available space jump, which moves the size range's `max`; a bound range left with a shifted `max` can stay stuck at its browser-computed midpoint, and because `addSizeMB` didn't itself change value Svelte's `bind:value` never re-wrote the DOM to unstick it. Added an effect that re-asserts a valid value on the slider whenever available space changes (clamped to the slider's own `max`, so a large typed value isn't pulled back down). This never fires an input event, so it doesn't fight user drags or the shared binding. Removed the temporary `[MANSLIDER]` debug logging that had been added to shadow the issue.
- **Manual partitioning rejects an ESP below 128 MiB or a system partition below 8 GiB** — the manual editor let the user designate any size, so a 1 MiB row could be assigned System (or a tiny ESP created) and pass the UI, then only fail later at install. Added an enforced floor matching the automatic installer: `shared.MinESPSizeBytes` (128 MiB) and `shared.MinSystemPartitionBytes` (8 GiB, the disk floor). `Validate` rejects a designated ESP/System row whose size is below the floor, computed byte-exactly for existing rows (MiB fallback for brand-new ones). A "use all remaining space" row (sizeMB 0) is exempt — its size is whatever the disk leaves. The frontend mirrors this in a new `isManualLayoutValid` used by the Disk Selection page gate, so "Next" stays disabled until the designated partitions meet the floor. The new constants are auto-emitted to `frontend/src/lib/constants.ts` and covered by `TestValidate_MinPartitionSizes` and `frontend/src/lib/store.test.ts`.
- **Manual partitioning no longer rejects a brand-new partition that replaces a deleted one** — `Validate`'s strict, sector-free-space check read `layout.FreeSectors`, which `ComputeLayout` stamps at disk-load time and is never updated after the user edits the plan. Deleting an existing row and adding a brand-new one in its place frees real room, but the stale free-space value still reflected the original layout, so a valid plan (the frontend recomputes free space correctly and enables "Next") was hard-rejected by the backend (`new partition sizes exceed the free space`). Fixed by recomputing free space in `Validate` from the live partition list: existing rows are counted by exact byte size (MiB fallback), brand-new rows are skipped since `newSectors` already accounts for them, and deleted rows are naturally excluded (they live on `DeletedPartitions`, not `Partitions`). The coarse MiB-sum guard and the genuine-overflow rejection are unchanged. Added `TestValidate_NewPartitionFreesSpaceFromDeletedRow`.
- **Manual partitioning no longer over-allocates a brand-new partition's size from truncated MB** — the free-space allowance counted existing partitions rounded *down* to MiB, but the partitions occupy their exact raw sectors, so free space was overstated by roughly the summed truncation remainders (~1 MiB per existing partition). On a Windows dualboot (4–6 kept partitions) an explicit new partition could pass the UI limit and `Validate` (both compare truncated MB against truncated disk size) yet then fail at `createPartition` with `partition extends past the last usable sector of the disk`. Fixed by carrying byte-exact geometry end-to-end: `shared.ManualLayout` gains `DiskSizeBytes` and `FreeSectors`, and each existing `shared.ManualPartition` now carries `SizeBytes`. `Validate` checks brand-new explicit partitions against free space *in sectors* (keeping the coarse MiB sum as a fallback), and `buildActions` measures free space in sectors too, clamping an explicit new-partition size to the true usable end instead of the requested value. `ComputeLayout` populates the new fields. The frontend `computeFreeMB` is now derived from byte-exact totals (`diskSizeBytes − Σ usedBytes`) so the UI allowance matches the backend. Added `TestValidate_NewPartitionRespectsFreeSectors` and `TestBuildActions_ClampsExplicitNewPartition`.
- **Manual partitioning no longer forces a 1 MiB partition when less than 1 MiB is free** — `buildActions` clamped an empty/free result to `available = 2048` sectors, carving a 1 MiB partition into a gap too small for it, which `sgdisk` rejected as extending past the last usable sector. Now clamps to 0 instead (an empty result), so a genuinely full disk yields nothing rather than an out-of-range partition. Covered by `TestBuildActions_ClampsExplicitNewPartition`.
- **Manual partitioning rejects a brand-new partition added after a "use all remaining space" one** — `Validate` only counted how many `sizeMB == 0` rows existed, not their order, so a "use remaining" row followed by another new partition would consume the disk then leave the second orphaned. Now `Validate` tracks whether a brand-new use-all row has appeared and rejects any further brand-new partition after it. The frontend already prevented this (adds are appended last and clear `availableAddMB`); this is the backend backstop. Added `TestValidate_UseAllOrdering`.

### Changed
- **Manual-mode disk space summary now displays in GB instead of MB** — the allocated/free bar labels in the disk top bar now convert the underlying MB values to GB (one decimal place, e.g. `1535.5 GB`) instead of showing raw megabytes. The formatter returns a bare number and the unit is emitted once by the label, so values never render a doubled `GB GB`.
- **Manual-mode disk space label renamed from "Allocated" to "Used"**.
- **Manual partitioning now counts an added partition in the space bar immediately** — `computeUsedMB` previously only counted partitions already designated (ESP/System) or existing on disk, so a brand-new row added via "Add" was invisible to the top-bar used/free bar: the drag preview (`pendingAddMB`) reset to 0 on Add and the bar jumped back to its pre-drag value. Now every row in the plan reserves its space, so the bar reflects the addition right away (before designation). The backend still ignores undesignated (Preserve) rows when creating partitions, so install behavior is unchanged.
- **Manual partitioning leaves 2 MB unallocated at the end of the disk** — "Use remaining" and the size slider now stop 2 MB short of full free space (`availableAddMB = freeMB − 2`), so partitions never carve the final bytes and a small alignment band stays untouched. `canAdd`, the slider/input `max`, the Add handler, and the space-bar preview all use the reduced amount.
- **Disk selection now shows a border around a disk icon when it isn't selected** — the unselected `disk-icon` gets a `1.5px` border; the selected icon clears its border color so it sits cleanly on the primary background.

### Fixed
- **Manual partitioning "Use remaining" is now a proper toggle switch instead of a native checkbox** — the bare browser checkbox in the add-partition row looked inconsistent with the rest of the wizard. Replaced it with an accessible styled switch: the native input is visually hidden but still keyboard/click reachable (focus-visible ring), the track takes the primary color and the knob slides across on toggle. No behavior change — it still toggles `addUseRemaining`, disabling the size slider and consuming the full free space.
- **Manual partitioning "Add" now previews the size in the top-bar space bar** — the manual page's size slider only changed local state, so the allocated/free bar in the disk top bar (driven by the shared layout) never moved while dragging. The pending "add partition" size is now written to a new `installState.pendingAddMB` on every slider change (clamped to available free space; "Use remaining" maps to the full free space), and `DiskSelectionPage` folds it into its used/free/pct summary so the bar live-updates before the partition is committed. The committed layout is unchanged — the preview is frontend-only and resets once the partition is added.
- **Partition scan no longer relies on a `sgdisk -p` output format it never reliably produced** — `partitionSectors` matched a prose line (`Partition \d+ is start sector …`) via regex, but `sgdisk` actually prints a whitespace-aligned table (`Number / Start (sector) / End (sector) …`) that the regex never matched, so it parsed no partitions. Replaced with a field-based parser that reads the first three integer columns of each row (new `parsePartitionSectors`), which naturally skips the header and free-space summary lines. Added `partition_sectors_test.go` with real `sgdisk -p` output guarding the parser.
- **Manual partitioning no longer wastes ~2 MiB at the front of the disk or a 1 MiB gap between partitions** — `buildActions` computed each new partition's start as `alignUp(maxEnd+1, 2048)`, but `maxEnd` was already the *next free* sector for brand-new partitions (and initialized to the first usable sector, 2048). On a wiped disk the first partition landed at sector 4096 instead of 2048 (a visible ~2 MiB free region at the front), and whenever a preceding partition ended exactly on a 1 MiB boundary the next partition started a full MiB later (a 1 MiB free gap between them) — e.g. a 512 MiB EFI followed by root showed vda1 at 4096 and a 1 MiB gap before vda2. Fixed by making `maxEnd` consistently the next-free sector (existing partitions contribute `end+1`), and dropping the `+1` so new partitions are placed at `alignUp(maxEnd, 2048)` and sit edge-to-edge. The automatic install path (`format.Run`) was unaffected (it already starts at 2048 and builds contiguously). Added `TestBuildActionsEmptyDiskNoStartGap` and `TestBuildActionsContiguousAfterAlignedPartition`, both of which fail against the old code (ESP at 4096, root 1 MiB late) and pass with the fix.
- **Manual partitioning: the delete button now actually removes the partition from the disk** — clicking delete removed the row from the in-memory layout and its space from the free/allocated totals, but `partition.Apply` (the only code that touches the real disk) only ever created new partitions and set GPT type GUIDs; it never ran `sgdisk -d`, so a deleted partition survived the install untouched. Removed partitions are now carried on the layout in a new `ManualLayout.DeletedPartitions` list (the frontend moves a row there on delete, keeping its device path/number) instead of being dropped, and `Apply` deletes them with `sgdisk -d <num>` (highest number first, so surviving partition numbers are unaffected — `sgdisk` does not renumber) followed by `partprobe`, before re-reading the disk geometry and creating any new partitions. Verified end-to-end in the QEMU test VM: a layout that keeps an existing ESP + an existing Root and deletes the middle partition leaves only the two kept partitions on disk, with the surviving Root correctly re-typed to the Linux-root GUID.
- **Manual (dualboot) partitioning via the CLI never actually created new partitions** — `partition.createPartition` built the `sgdisk` argument list (`-n`, `-t`, `-c`) but never appended the disk path, so `sgdisk` ran with no target device. With no disk argument and stdin closed, `sgdisk` returned success (RC 0, empty output) while creating nothing, so the format step then failed on `wipefs /dev/vdaN: No such file or directory`. Two follow-on defects surfaced once partitions were finally created: `Apply` read the ESP/System device paths from the layout rows, whose `Path` is empty for brand-new partitions (the real path like `/dev/vda1` only exists in the `formatAction` from `buildActions`), so `readUUID` ran `blkid` on an empty path (`blkid : exit status 2`); and the mount step mounted at `/mnt` without ensuring the directory existed, which a bare live-ISO rootfs does not provide (`mount: mount point does not exist`). Fixed by appending `diskID` to the `sgdisk` args, resolving the ESP/System paths from the format actions, and mounting the root partition with `mount --mkdir`. Verified with a real end-to-end manual install in the QEMU test VM (`--manual-layout` with a new 512 M ESP + rest-of-disk System): all seven steps pass and `verify-system` reports the installed system valid, with fstab correctly listing the ext4 root and vfat EFI partitions.

### Added
- **Confirmation summary page now supports manual (dualboot) installs, not just automatic** — the summary previously showed a single whole-disk "selected filesystem", which only makes sense for automatic installs. In manual mode it now renders a read-only partition-plan table listing every planned row: path (or "New partition"), size (MB), role (ESP/System/Preserve, colour-coded), mountpoint (ESP → /boot, System → /, Preserve → —), and filesystem (ESP → VFAT, System → the chosen root fs, Preserve → the existing fs, left untouched). Designated rows are highlighted to match the partition editor. The confirmation dialog is now mode-aware too: automatic installs keep "All data on this disk will be permanently erased", while manual installs say "Only your chosen Boot and Root partitions are touched — your other partitions and data are left untouched". The dialog also moved out of `App.svelte` into `ConfirmationPage.svelte`, so it lives on the page that owns it (mirroring how ManualPartitionPage owns its delete dialog); `ConfirmDialog` still accepts an explicit `message` for the delete flow. New keys `page.confirmation.mount`, `page.confirmation.filesystem`, `fs.vfat`, and `dialog.confirm.messageManual` (English fallback for other locales). `svelte-check` (0 errors, 0 warnings) and `vitest` (45 tests) pass.
- **Manual partitioning role selector is now a light-themed custom dropdown instead of a native `<select>`** — the per-row type selector was a native `<select>`, whose options popup is drawn by the OS/browser and can't be recoloured, so it rendered a dark list over the installer's light theme. Replaced it with a new `frontend/src/components/RoleSelect.svelte` component following the ARIA listbox pattern (a trigger button with `aria-haspopup`/`aria-expanded`/`aria-controls`, a `role="listbox"` menu, and `role="option"` rows). The trigger is a themed pill showing the current role (ESP/System/Preserve) with a colour-coded chevron; the menu is fully themed to the installer's light tokens and closes on outside-click, Escape, or after picking. The control fits its label instead of stretching the cell width and left-aligns in its cell (the type cell now sets `text-align: start` to override the document-wide center alignment). Assignment behaviour is unchanged — it still flows through the existing `setType` → store → persist path, and re-selecting the active role still clears it back to Preserve. Covered by `svelte-check` (0 errors, 0 warnings) and the existing 45 `vitest` tests.
- **Manual partitioning slider warning fixed** — `sliderEl` (bound via `bind:this` to the add-partition range input) was a plain `let`, so Svelte 5 flagged it as a non-reactive update (`svelte.dev/e/non_reactive_update`). Declared it with `$state<HTMLInputElement | null>(null)`; `svelte-check` now reports 0 warnings. No behavior change.
- **Confirmation dialog reused for manual-partition deletion with a unified mauve-pink action button** — the install-confirmation modal (`frontend/src/components/ConfirmDialog.svelte`) is now a single shared component used on both the Confirmation page and the Manual Partition page's delete flow, so both dialogs render identically. The component is parameterized via Svelte 5 props (`title`, `message`, `cancelLabel`, `confirmLabel`, `showIcon`, `onConfirm`, `onCancel`); when no `onConfirm`/`onCancel` are passed it keeps the original installation flow (dispatches `go-next-confirmed`, advances the wizard), and pages with their own state (e.g. delete) pass their own callbacks. The delete dialog previously had its own inline modal with a red danger button; it now uses the shared component with manual-specific text and no warning glyph (`show-icon={false}`, later removed so both dialogs share the red warning icon). The red `danger` button styling and `.dialog.danger` shadow were removed entirely, so the action button is one unified mauve-pink style (`--color-primary`) matching the summary page's "Yes" button. The now-orphaned delete-dialog CSS block was deleted from `frontend/src/pages/ManualPartitionPage.css`. `svelte-check` and `vitest` (45 tests) pass.
- **Playwright end-to-end testing suite for the installer frontend** — new `frontend/playwright.config.ts` + `frontend/e2e/` specs (`wizard.spec.ts`, `install.spec.ts`) that drive the real Wails app through Playwright. Because the pages call Go backend bindings via the Wails runtime, tests run against `wails dev` (auto-started via Playwright's `webServer` option) with `FAKE_DISKS=1` and `AELUM_DRY_RUN=1` so the wizard has synthetic disks to select and install steps finish quickly. Added `@playwright/test` devDependency and `e2e` / `e2e:headed` / `e2e:install` / `e2e:report` npm scripts. `wails.json` `frontend:dev:serverUrl` pinned to a fixed `http://localhost:34115` so the config `baseURL` is stable. Tests cover Welcome, user-account validation, disk/filesystem selection, confirmation summary, back navigation, and the full flow through the Installation step. See `frontend/e2e/README.md`. Note: the dry-run CLI validates the synthetic disk layout and reports an ESP error, so the automated flow lands on the Installation error hint rather than Finish — the test accepts either terminal state.

### Fixed
- **Scroll position in the language and disk lists is now preserved across page switches** — the `ScrollBox` container (used for the language list and disk list) now saves its scroll position while scrolling and restores it when the page is remounted. App.svelte wraps each page in `{#key navState.currentPage}`, so switching pages (or toggling automatic/manual mode in Disk Selection) unmounts and remounts the list and would otherwise jump back to the top. Positions are keyed by page id and stored on `globalThis` rather than a module-level `Map`, because the running app re-evaluates the `ScrollBox` module on each page remount (a module-level map was observed empty on return, while the window object persists for the app's lifetime). The position is only captured while the scroll element is still attached to the document, so teardown (which reads `scrollTop` as 0 on a detached element) no longer clobbers the last live value. The Welcome page id (`0`) is handled as a valid key, not a falsy one.
- **Manual partitioning: every partition is now deletable** — the delete button was gated by `canDelete`, which only allowed removing brand-new or designated Boot/Root partitions. That forced users to first assign a role to an existing partition just to remove it, a confusing detour since deletion and role assignment are independent concerns. Removed the `canDelete` gate and the button's `disabled` binding so every row's delete button always opens the existing confirmation dialog, which remains the safety gate for the destructive action. (This reverses the earlier "deleting an untouched (preserve) partition is blocked" fix.)
- **Manual (dualboot) partitioning: new partitions can no longer overlap kept partitions** — `buildActions` seeds its placement frontier (`maxEnd`) from a fresh `sgdisk -p`, but the only test exercising it asserted partition *numbers*, not geometry, so a regression that carved a new partition into a preserved OS/data partition would have gone undetected. Added `TestBuildActions_NoOverlapWithExisting`, which asserts every new partition starts at/after the end of all existing partitions and stays within the disk, and that preserve partitions are never formatted. Verified the test fails when the frontier logic is broken.
- **Manual partitioning: deleting an untouched (preserve) partition is blocked** — `canDelete` allowed removing a preserve row from the plan, but the installer never references such partitions, so the delete was a no-op on disk while the confirmation warned it "returns its space to unallocated." Preserve rows can no longer be deleted; only brand-new and designated Boot/Root partitions can be removed from the plan.
- **Manual partitioning: type pills no longer clear a role by accident** — clicking an already-assigned type was a toggle-off, which could silently leave an invalid layout (zero ESP/zero System). Clicking the active type is now a no-op; use the delete button to remove a designation.
- **Manual partitioning: navigation shows the specific validation error** — advancing from the Disk Selection page returned a generic "select a disk" prompt for any manual-layout failure. It now surfaces the backend's exact reason (e.g. "exactly one ESP partition is required", partition sizes exceed the disk).
- **`parsePartitionNum` handled only nvme0/nvme1** — the hardcoded `nvme0n1p`/`nvme1n1p` prefixes would mis-parse higher-index NVMe disks (e.g. `/dev/nvme3n1p12`). Replaced with a regex for any `nvme<n>n<m>p<part>` index plus a trailing-digit fallback for conventional names.
- **Manual partition "Add" can no longer over-allocate beyond free space** — the Add button was only disabled when free space hit zero, but `addPartition` only rejected sizes ≤ 0, so an explicitly-typed size could exceed the disk. Now rejects an explicit size greater than the available free space (the "Use remaining" option is unaffected, as it already consumes exactly the free space).
- **Disk Selection filesystem detection no longer keeps a duplicate disk copy** — when the filesystem was derived from existing partitions, the code mutated the shared disk object and then assigned a separate shallow copy to `installState.disk`, so the disk card, sidebar, and manual editor could read divergent data. It now updates the single disk object in place and points `installState.disk` at that same object.
- **Manual mode without a disk shows a proper, centered message instead of a raw key** — the no-disk manual screen called `t('page.diskSelection.selectDiskManual')`, which did not exist in any locale, so the app fell back to showing the literal key text on an otherwise blank page. Added the `page.diskSelection.selectDiskManual` and `page.diskSelection.selectDiskFirst` keys (en-US) and made mode switching driven by a single `manualMode` flag: selecting Manual without a disk now highlights the Manual pill and shows a centered "Select a disk…" message, and switching back to Automatic returns to the disk list.

The card is now a compact one-line row (icon, model/name, size + HDD/SSD + transport, selection radio). The disk is still selected on click; only the on-click info dropdown and its tags were removed.

The bar and labels were swapped so the bar sits directly under the disk name.

Note: bumping the Go toolchain alone does not fix this panic — Go was already at 1.27 locally, which is what triggered it. The fix is the staticcheck/golangci-lint upgrade, not a newer Go.

Replaced the weight-derived durations with a single `shared.DryRunStepDurationMs` (1000) constant used by both the step simulation and the tick goroutine. Progress-bar distribution still follows the real step weights; only the simulated per-step duration is now flat. This keeps the E2E/wizard flow fast and predictable without touching the real install timing.
- **Going back from the Confirmation page no longer clears the disk selection** — previously `goBack` reset `installState.diskId`/`installState.disk` when leaving Confirmation, so a single mis-click on Back discarded the whole disk choice and forced re-selecting. The reset was removed; the selection now persists across the Confirmation round-trip. Updated the App navigation test to assert the disk is preserved.
- **Removed the installer's manual-partition GPT-overhead reservation** — the layout math previously subtracted a fixed 1 MiB (`GPTOverheadMB`/`GPTOverheadBytes`) from free space and required `ΣpartitionSizes + 1 MiB ≤ diskSize`. Real partition tools (sgdisk/gdisk/parted) place the backup GPT automatically and accept partitions that fill the disk, so the installer no longer models this overhead. Free-space derivation (`ComputeLayout`, frontend `computeFreeMB`), the "use all remaining space" size, and the size-fit validation all drop the 1 MiB term; the validation still rejects layouts whose partitions exceed the disk. Removed the now-obsolete `GPTOverheadBytes` constant and `TestGPTOverheadBytes`. As a result a fully-allocated disk (e.g. the first fake disk) is now a valid manual-install target instead of being rejected for lacking GPT headroom.
